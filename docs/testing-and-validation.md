# Testing and validation

## Strategy
1. **Hand-calculated correctness tests** (`backend/tests/test_algorithms.py`). Each expected schedule was computed by hand from the rules in `algorithm-specifications.md` before the engine ran. When a test disagreed, the engine trace was examined first. Two expectations were corrected after that check confirmed the engine followed the documented rules (an RR/priority FIFO tie, and an AQS burst too short to reach nine dispatches).
2. **Differential tests against an independent reference model** (`test_reference_model.py`). A second simulator, written only from the specification and structured differently (monotonic sequence numbers instead of list order, one function, no policy classes), must produce the **same tick-by-tick schedule** as the engine for all 7 algorithms, with and without I/O, at switch costs 0, 1 and 3, on random workloads with ties and idle gaps (78 parameter combinations × 80 workloads). A guard test checks that AQS really moves its quantum in those workloads, so the AQS comparison cannot be vacuous.
3. **Mutation testing** (`scripts/mutation_check.py`, repeatable). Deliberately breaking the engine in 10 ways must make the suite fail: SRTF preempting on ties, requeue-before-arrival order, priority ageing off by one, MLFQ demotion on block / boost off by one / preempt on equal level, AQS overhead rule disabled / step doubled / window ignoring overhead, switch counted for the same process. All 10 were caught, then the originals were restored. The same was done for the compact codec (5 of 5 caught).
4. **Property tests** (`test_engine_properties.py`): every algorithm × every preset × switch cost {0, 2}: accounting invariant, segments tile `[0, end]`, executed CPU per process equals its bursts, switch segments = switches × cost, frame states consistent with queues.
5. **Validation, limits, determinism and analysis:** invalid workloads and configs, the documented limits (100 processes, 50,000 tu horizon, burst and arrival bounds), generator determinism, simulation determinism, percentiles, Jain index, compare deltas, sweeps and trials.
6. **Compact result format** (`test_compact.py`, `frontend/src/lib/compact.test.ts`): `expand(compact(r)) == r` for every algorithm × preset × cost and for random workloads; reverse-order frame equality; size guards (≥ 8× smaller, ≈ 1.5 stored rows per frame). A **golden fixture** generated by the engine is decoded by the TypeScript decoder and must equal the engine's full result; a backend test fails if the fixture is stale.
7. **API and persistence** (`test_api.py`): all endpoints, structured 422/404, result detail modes, lean `compare`, gzip, CRUD, server-side rerun on save, reproducibility, history paging, migration of a first-release database, concurrent saves, restart persistence, static-file path-traversal guard.
8. **Frontend:** strict `tsc`, Vitest (workload validation, colours, formatting, CSV, Gantt chart, compact decoder, API client including the older-backend fallback), and the production build.
9. **Browser end-to-end tests** (Playwright/Chromium): 9 workflow tests plus the **18-step faculty demonstration** (`e2e/demo.spec.ts`). Every test fails on any console error; the demo test also fails on any request that leaves localhost and cross-checks the exported results against an independent engine run.
10. **Performance probe** (`npm run perf`, from `frontend/`): 100 processes in a real browser; payload, time to render, playback frame rate at the start and at 80 % of the run.

## How to run
```powershell
.\scripts\test.ps1      # pytest + typecheck + vitest + build
.\scripts\run-e2e.ps1   # Playwright on a private port with a temporary database (first: cd frontend; npx playwright install chromium)
cd frontend; npm run perf -- http://127.0.0.1:8000     # large-workload probe against a running server (uses a 100-process workload)
```
```powershell
backend\.venv\Scripts\python.exe scripts\mutation_check.py   # patches one line at a time, runs the suite, always restores the file
```

Developer utilities (not tests): `frontend/e2e/shoot-pages.mjs` (screenshots every route, desktop and mobile), `frontend/e2e/shoot-charts.mjs` (renders the research SVG charts to PNG). Both take an output directory. `shoot-pages.mjs` saves experiments, so point it at a server that uses a temporary database (`SCHEDX_DB`).

## Not tested
`start.ps1 -Dev`; Firefox and Safari; physical mobile devices; Python versions other than 3.14; automated accessibility tooling; very large saved-experiment histories.
